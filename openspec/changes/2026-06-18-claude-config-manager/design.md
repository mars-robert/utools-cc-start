# Claude Config Manager Design

## Context

当前 uTools 插件已经有一个统一配置中心，但它管理的是启动器和命令列表。现在要新增的是对 `~/.claude.json` 的图形化配置管理，而不是纯文本编辑器。

这个功能的目标是：把当前已知的 Claude 配置项做成可视化、可校验、可写回的表单界面，体验接近 VS Code 的设置页。

## Goals

- 以表单方式查看和编辑 `~/.claude.json`
- 按配置分类展示字段，并为每个字段提供说明
- 保存前进行类型校验、必填校验和基础约束校验
- 保存时将结构化数据写回原 JSON 文件
- 写回前保留备份，避免配置损坏后无法恢复
- 支持“恢复到上次保存状态”和“恢复默认值”

## Non-Goals

- 不做通用 JSON 文本编辑器
- 不做任意未知字段的自由增删改
- 不追求对未来所有 Claude 配置变体自动兼容
- 不在第一版里做跨平台深度差异化适配，先以当前已知结构为准

## Decisions

### 决策 1: 采用 schema 驱动表单

所有可编辑配置项都来自一份本地 schema。Schema 定义字段所属分组、标题、说明、控件类型、默认值、校验规则、是否必填，以及字段之间的依赖关系。

这意味着页面不是从 JSON 动态猜测生成，而是从“已知配置模型”渲染。这样可以做到：

- 控件类型稳定
- 错误提示可控
- 说明文案可以人工优化
- 后续扩展字段只需要补 schema

### 决策 2: 以分组导航 + 详情表单作为主界面

界面采用左右布局：

- 左侧：配置分组导航
- 右侧：当前分组的表单内容

每个字段块包含：

- 字段标题
- 简短说明
- 输入控件
- 校验提示
- 默认值提示

如果某个分组字段较多，可以在右侧内部分段折叠，但第一版优先保持直接可见。

### 决策 3: 写回前先做完整校验，再备份再落盘

保存时按以下顺序执行：

1. 收集当前表单值
2. 按 schema 做字段级校验
3. 按 schema 做跨字段依赖校验
4. 将结构化数据序列化为 JSON
5. 保存原文件备份
6. 覆盖写入 `~/.claude.json`
7. 重新读取文件并验证写回结果

如果任一步失败，保留原文件不变，并把错误显示在对应字段或顶部错误区。

### 决策 4: 只管理“当前已知结构”

用户已经明确要按照当前已知结构实现，因此本功能的边界是：

- 仅渲染 schema 中声明的字段
- 仅支持 schema 中定义的写回逻辑
- 对 schema 之外的字段不做编辑支持

这样可以避免把功能退化成通用编辑器，也降低后续维护成本。

## Information Architecture

### 页面入口

建议在现有统一配置中心中新增一个子页，例如：

- 启动配置
- 快捷命令
- Claude 配置

这样用户不会误以为这是一个独立工具，也符合当前插件的“统一配置”定位。

### 左侧导航

导航项按配置主题分组，例如：

- 基础
- 身份与账户
- 项目与工作区
- 行为偏好
- 高级

分组名称不必严格绑定最终的 JSON key，而是按用户理解来组织。

### 右侧内容区

每个配置分组以卡片或分段形式展示。字段多的分组可以继续拆成子节，每节控制在 5 到 8 个字段以内，避免页面过长。

### 底部操作栏

固定显示：

- 恢复默认
- 撤销未保存修改
- 保存

保存按钮在无修改时禁用，或保持但呈弱状态。

## Field Model

每个 schema 字段建议包含以下元数据：

- `key`: JSON 路径或字段名
- `label`: 显示名称
- `description`: 说明文案
- `group`: 所属分组
- `type`: `string` / `number` / `boolean` / `enum` / `path` / `multiline`
- `defaultValue`
- `required`
- `placeholder`
- `options`: 枚举项
- `validation`: 规则集合
- `dependsOn`: 依赖字段
- `transform`: 写回时的值转换器

其中 `transform` 用于处理与 UI 输入不一致的情况，例如：

- UI 使用开关，但 JSON 里需要显式布尔值
- UI 使用路径选择器，但 JSON 里需要标准化路径字符串
- UI 使用枚举标签，但写回需要枚举原始值

## Validation

校验分三层：

1. 字段级校验
2. 分组内校验
3. 全局校验

字段级校验包括：

- 必填
- 类型
- 数值范围
- 字符串长度
- 正则格式

分组内校验用于检查互斥项或依赖项，比如某些字段只有在某个开关开启后才允许编辑。

全局校验用于检查最终 JSON 是否可序列化、是否满足 Claude 读取要求，以及是否存在明显冲突。

校验结果应直接绑定到字段附近，而不是只在顶部弹一个通用错误。

## Read / Write Flow

### 读取

1. 读取 `~/.claude.json`
2. 如果文件不存在，则使用 schema 默认值生成一个新草案
3. 如果 JSON 语法错误，则展示解析错误，并允许用户进入修复模式
4. 将 JSON 映射为表单状态

### 编辑

1. 用户修改字段
2. 页面实时标记未保存
3. 相关字段触发联动刷新和即时校验

### 保存

1. 对当前表单进行全量校验
2. 生成规范化 JSON
3. 备份原文件
4. 写入目标文件
5. 重新读取并验证

### 恢复

提供两类恢复：

- 恢复到上次保存状态
- 恢复到 schema 默认值

两者语义要分开，避免用户误以为“恢复默认”只是在撤销这次编辑。

## Error Handling

### 文件不存在

如果 `~/.claude.json` 不存在，页面展示空状态，并给出“创建配置文件”的按钮。此时保存会创建新文件。

### 文件无法解析

如果文件存在但 JSON 语法错误，页面进入错误状态：

- 显示错误行或错误摘要
- 保留可复制的原始内容摘要
- 提供重新加载和退出选项

### 保存失败

如果写入失败：

- 保留当前表单状态
- 提示明确错误原因
- 不覆盖原文件

### 校验失败

如果校验失败：

- 不允许保存
- 将错误精确定位到对应字段
- 第一条错误可自动滚动到可视区域

## Data Safety

保存前必须创建备份，例如：

- 原文件复制为 `.claude.json.bak`
- 或保留时间戳备份，例如 `.claude.json.bak-20260618-1200`

第一版建议使用时间戳备份，避免覆盖上一次备份。

恢复逻辑优先使用最近一次有效备份。

## UX Notes

- 页面标题要明确显示当前编辑的是 `~/.claude.json`
- 顶部显示文件状态：
  - 已加载
  - 未保存
  - 有错误
- 字段说明不要太长，长说明折叠到帮助提示中
- 对危险字段或容易误解的字段做二次确认
- 保存成功后给出简短结果摘要，而不是只提示“成功”

## Integration With Existing App

建议接入现有 `UnifiedConfig`，作为新增配置页，而不是新入口。

原因：

- 当前插件已经有统一配置中心的结构
- 新功能本质上属于“配置管理”，不需要分散入口
- 这样用户更容易发现入口，也更符合现有信息架构

## Risks

- 当前已知结构如果和实际 Claude 版本不一致，schema 需要调整
- 如果字段很多，单页会过长，需要后续再拆分导航
- 如果配置文件里存在大量 schema 之外的内容，第一版会选择不支持编辑

## Open Questions

没有未决的产品方向问题。当前已确认：

- 采用图形化配置，不做纯文本编辑器
- 按当前已知结构实现
- 保存时更新 JSON 文件
