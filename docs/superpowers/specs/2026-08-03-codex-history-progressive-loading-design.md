# Codex 历史会话渐进式加载设计

## 背景

Codex 历史页当前在 Vue 渲染线程中同步执行两类查询：

1. 从 `~/.codex/state_5.sqlite` 读取并按 `cwd` 筛选历史会话；
2. 从 `~/.codex/logs_2.sqlite` 与 `state_5.sqlite` 计算当前活跃会话。

uTools 7.8.0 使用 Electron 22.3.27，其 Node 运行时不支持 `node:sqlite`。现有 preload 因此退化为 `spawnSync('node', ...)`。页面只有在历史列表与活跃状态都同步完成后才能绘制；活跃状态又每 2.5 秒同步刷新，导致首屏延迟和周期性卡顿风险。

## 目标

- Codex 历史列表返回后立即渲染，不等待活跃状态。
- SQLite 查询和活跃会话计算不阻塞 Vue 渲染线程。
- 活跃状态仍自动刷新，但同一时刻最多存在一个查询。
- 项目切换或页面卸载后，旧请求不得覆盖当前页面状态。
- 外部 Node 不可用、查询失败或超时时，页面保持可用且不触发同步重试。
- Claude Code 历史加载和轮询逻辑保持不变。

## 非目标

- 不引入原生 SQLite 依赖。
- 不修改 Codex 数据库结构或索引。
- 不改变历史详情 JSONL 的解析与渲染逻辑。
- 不改变 2.5 秒的活跃状态刷新频率；性能隔离由异步执行和请求去重保证。

## 方案

### 1. 异步外部 Node 查询

preload 新增 Codex 专用异步 API：

- `listCodexProjectSessionsAsync(cwd)`
- `listActiveCodexSessionsAsync(cwd)`

两者使用 `spawn('node', ['-e', script])`，不再从页面路径调用 `spawnSync`。子进程负责 SQLite 查询和数据筛选，preload 只解析最终 JSON。

历史列表子进程优先查询 SQLite；SQLite 不可用时也由该子进程扫描 `~/.codex/sessions`，最后返回目标 `cwd` 的非 subagent 会话元数据。活跃状态子进程完成以下全部工作后，只返回少量 `{ sessionId, status, pid }`：

1. 查询最近的日志记录与 thread 元数据；
2. 按 `process_uuid` 保留最新 thread；
3. 按规范化 `cwd` 过滤；
4. 检查 PID 是否存活；
5. 去重并输出最终活跃会话。

这样 Vue 线程不再处理 `logs_2.sqlite` 返回的大块中间数据。

现有同步 API 保留，供既有调用和测试兼容；Codex 历史页改用异步 API。Claude 路径继续使用原接口。

### 2. 进程执行边界

异步执行器负责：

- 捕获 `stdout` 与有限长度的 `stderr`；
- 限制输出大小，超过上限时终止子进程并返回失败；
- 3 秒超时后终止子进程；
- 只接受退出码为 0 且能解析为预期结构的 JSON；
- 保证 resolve 一次，并清理定时器与监听器。

历史列表子进程无法启动、超时或返回坏数据时直接报告失败，不在 preload 中执行同步文件扫描或同步外部 Node 重试。活跃状态查询失败时由页面保留上一次成功结果，不执行同步兜底。

### 3. 页面渐进式加载

Codex 页面加载顺序：

```text
进入页面
  -> 异步加载历史列表
  -> 校验请求仍属于当前项目
  -> 写入 sessions，等待 Vue 完成一帧渲染
  -> 异步刷新活跃状态
  -> 补充“进行中”标记
```

页面维护递增的加载版本号。每次项目变化或卸载时版本递增，异步结果只有在版本仍匹配时才能写入状态。

活跃状态刷新维护一个 in-flight Promise。同一查询未完成时，2.5 秒定时器直接复用或跳过该请求，不创建并发子进程。失败时保留已有活跃状态，首次失败则保持空集合。

Claude 页面继续沿用当前同步列表加载和活跃检测，不经过新的 Codex 协调逻辑。

## 错误处理

- 历史列表失败：显示现有错误信息；文件扫描成功时正常展示降级结果。
- 活跃状态失败：不影响列表和详情，不向用户弹出阻断错误。
- 子进程超时、启动失败、输出过大、JSON 损坏：统一视为本次异步查询失败。
- 项目切换后的迟到结果：静默丢弃。
- 页面卸载：停止定时器并使在途结果失效；已启动的子进程自行结束，最迟在 3 秒超时后被执行器终止。

## 测试

### preload 单元测试

- 异步历史查询成功时按 `cwd` 过滤、排除 subagent 并排序。
- 异步活跃查询只返回当前项目、存活 PID 对应的最新 thread。
- 子进程失败、超时、输出过大和坏 JSON 均能结束 Promise，且不调用同步外部 Node 兜底。
- 同步 Codex API 继续通过既有测试。

### 页面加载协调测试

抽取小型纯逻辑协调器，使用可控 Promise 验证：

- 列表写入发生在活跃查询完成之前；
- 同一时刻只有一个活跃查询；
- 项目切换后旧列表和旧活跃结果被丢弃；
- 活跃查询失败不清空上一次成功状态。

### 回归验证

- 运行 Codex 历史、Claude 历史及启动器相关测试。
- 运行完整 `npm test` 与 `npm run build`。
- 在 uTools 中确认列表先出现、活跃标记随后补齐，持续操作时无 2.5 秒周期性卡顿。

## 成功标准

- 当前数据规模下，Codex 历史列表通常在 300 ms 内出现。
- 活跃状态查询耗时不计入列表首屏时间。
- 活跃查询期间滚动、点击和切换会话保持响应。
- 任意时刻最多运行一个活跃状态子进程。
- Claude 历史行为和测试结果不变。
